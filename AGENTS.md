# MetaDrive coding agent instructions

**MANDATORY:** Read and follow [DEVELOPER_POLICY.md](DEVELOPER_POLICY.md) in full before implementing any coding task. Its 24 rules are binding for features, bug fixes, migrations, refactors, installers, PRs and reviews.

**MANDATORY FOR STANDALONE APP UI MIGRATIONS:** Read and follow [MIGRATION_POLICY.md](MIGRATION_POLICY.md) before converting an existing standalone application into a separate `UNE <AppName>` Page Builder/AppExchange UI. Preserve the original app, reuse its existing backend Flows, use registered UNE components and the shared Property Engine, and keep all new components in the existing per-component folder structure. Do not replace the standalone app or duplicate backend workflows.

**PAGE LAYOUT REQUIREMENT (ALL APPS AND OBJECTS):** Treat Mobile, Desktop, Tablet and Custom as four independently editable Page Builder layouts for every App Page and Object Record Page. Use shared SQL layout metadata, publishing, assignments and runtime resolution; preserve tenant customisations, and do not claim Custom support already exists until implemented and verified. Apply this to [UNE AceChatter's migration plan](docs/UNE_ACECHATTER_MIGRATION_PLAN.md) and all subsequent app migrations.

Inspect existing metadata-driven Objects, Actions, Flows, registered Components, shared functions/loops and central RBAC before coding. Reuse existing platform engines; implement app behaviour through metadata instead of app-specific hardcoding. Seed appropriate metadata and initial permissions for every new app/module through the single central RBAC engine. **OneEngine is a configurable full-access-starting permission set, not a separate engine or hardcoded identity bypass.** Authorised administrators may grant, restrict and revoke its individual permissions using RBAC; tenant, entitlement and audited platform access boundaries still apply. Apply the modular code limits and temporary legacy exceptions in Policy §21; split by responsibility.

If a user request conflicts with any policy rule, explain the conflict and ask the owner to decide before implementing the conflicting change. Verify applicable architecture, functionality, security and tests before declaring completion. Never silently bypass this policy.
