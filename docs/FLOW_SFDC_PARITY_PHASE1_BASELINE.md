# Salesforce Flow Builder parity — Phase 1 baseline

Status: **Phase 1 evidence baseline**
Review date: **2026-10-28**
Scope: declarative Flow Builder capabilities described by Salesforce Trailhead; Apex is explicitly excluded.

## Purpose and evidence limits

This document records what repository evidence establishes today, what is only claimed by a contract, and what still needs direct runtime or product verification. It is the Phase 1 inventory and acceptance baseline for the remaining parity phases; it does not change Flow behavior or claim complete Salesforce compatibility.

The Salesforce comparison uses the currently published Trailhead materials:

- [Build Flows with Flow Builder trail](https://trailhead.salesforce.com/content/learn/trails/build-flows-with-flow-builder)
- [Flow Builder Basics module](https://trailhead.salesforce.com/content/learn/modules/flow-basics)
- [Flow type overview](https://trailhead.salesforce.com/content/learn/modules/flow-basics/get-started-with-flows?trail_id=build-flows-with-flow-builder)

Trailhead's trail covers Flow Builder basics, record operations, logic/formulas, record-triggered flows, screenless flows, screen flows, collection transforms/sort/filter, and loops. Its Flow type overview also names Data Cloud-triggered flows. The Trailhead material reviewed is not labeled for a seasonal Salesforce release; this baseline must not be presented as a verified release-note-by-release-note audit.

MetaDrive evidence was inspected in the Flow Builder, metadata types, capability registry, server validator/debugger, runtime node inventory, tests and Flow contracts listed below. A feature shown in metadata or a design contract is not by itself proof of end-to-end parity. Unless a row explicitly identifies a test or implementation, runtime parity remains unverified. No browser, PostgreSQL, or complete Flow test suite was run for this documentation-only phase.

### Status meanings

- **Present (repository evidence):** the feature is identifiable in Builder, runtime, metadata or tests. This is not a claim that every Salesforce variant matches.
- **Partial:** a narrower implementation or known limitation exists, or full feature breadth is unverified.
- **Missing:** no equivalent Flow type or capability was found in the inspected repository evidence.
- **Unresolved:** repository sources disagree or evidence is insufficient to classify accurately.

## Baseline conflicts requiring resolution

These are documentation/runtime evidence conflicts, not permission to choose a behavior. Phase 1 records them for the owning implementation phase to verify.

1. **Formula VLOOKUP:** [FLOW_PHASE3_CONTRACT.md](FLOW_PHASE3_CONTRACT.md) describes VLOOKUP over a bounded previously fetched collection; [FLOW_EXECUTION_CONTEXT_CONTRACT.md](FLOW_EXECUTION_CONTEXT_CONTRACT.md) says VLOOKUP is rejected by the formula runtime. Confirm actual parser/runtime behavior and tests, then make the contract consistent.
2. **Monthly schedules and limits:** [FLOW_PHASE3_CONTRACT.md](FLOW_PHASE3_CONTRACT.md) and [FLOW_PHASE5_ORCHESTRATION.md](FLOW_PHASE5_ORCHESTRATION.md) claim monthly recurrence and high-volume keyset dispatch; [FLOW_EXECUTION_CONTEXT_CONTRACT.md](FLOW_EXECUTION_CONTEXT_CONTRACT.md) describes only Once/Daily/every-seven-days Weekly and a 500-active-schedule scan cap. Verify current scheduler and production migrations; do not assert monthly or scale parity before then.
3. **Flow type availability:** the baseline capability migration initially disables creation for automatic flow types and orchestration. Later additive migrations unlock selected types. The Builder's metadata union is therefore not proof that a fresh tenant or a given tenant can create every type.
4. **Runtime evidence versus contracts:** design docs sometimes describe intended acceptance/release gates. A passed unit test, a registry row, or a contract statement alone does not establish authenticated browser-to-PostgreSQL release readiness.

## MetaDrive strengths to preserve

- **Safe graph editing:** refuses ambiguous branch rewires and preserves connector identity/metadata for supported operations; provides undo/redo and graph diagnostics.
- **Durable execution and recovery:** SQL-backed scheduling, wait/resume and approval flows use durable jobs, idempotency and explicit operator reconciliation for ambiguous side effects.
- **Shared capability governance:** the SQL registry drives both Builder visibility and production validation, with tenant entitlement and central authorization boundaries.
- **Controlled no-code integrations:** structured mappings use tenant-scoped HTTPS credentials, bounded inputs/outputs and durable dispatch rather than exposing secrets to the Builder.
- **Bounded execution:** record/collection/interview limits and explicit unsupported formula/transform features favor predictable and safer operation over claiming unbounded Salesforce behavior.

Parity work should preserve these properties; Salesforce parity does not require removing MetaDrive's deliberate safety and tenancy boundaries.

## Phase 1 deliverable and acceptance criteria

This document is the Phase 1 deliverable. Phase 1 is complete when:

1. Every Trailhead capability area in scope is marked Present, Partial, Missing or Unresolved, with evidence and a specific next proof/gap.
2. Apex is explicitly out of scope and Data Cloud-triggered flows are marked missing rather than inferred from other event flows.
3. Contract/code discrepancies are recorded as unresolved and are not represented as supported features.
4. Each later-phase work item can reference this inventory and has a measurable acceptance path.
5. No runtime, schema, permission, seed, or existing-flow behavior changes are included in this documentation-only phase.
